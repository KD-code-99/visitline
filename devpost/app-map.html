Where a changed need becomes a changed route

Visitline compares an organiser’s notes with the needs chosen for a visit, then creates a readable visitor card. This is a reference route through actual code. It has not been presented as a completed hands-on code tour.

Follow one real action

  1. Input — dist/app.mjs, search checks-form. The submit handler copies the current plan, reads the chosen needs and calls commit. Unfinished values in another form remain separate.
  2. Decision — dist/core.mjs, evaluateStage and evaluateRoute. Each included part can match, have a known problem, or need more information. A 96 cm doorway and 95 cm toilet route both fail a chosen 100 cm need. A missing measurement remains unknown rather than passing.
  3. Result — dist/app.mjs, render; dist/export.mjs, visitorHtml. The diagram, explanation, preview and downloaded card use that same decision. Text entered by users stays text, including in HTML exports.

A practice to reuse

The user found the terminology too technical. The interface changed from observations, stages and revisions to what was checked, parts of the route and plan versions. The underlying comparison stayed the same, and the real browser journey plus fixture tests were rerun. Treat understandable wording as part of the behavior to verify; a correct calculation alone does not establish that people understand it.

Run it again

node server.mjs
# Open http://127.0.0.1:4187
node --test

No dependency installation or API key is needed. Records and unfinished edits stay in the tab until a file is downloaded; refreshing closes that in-memory work. There is no record database or remote service in this action.
