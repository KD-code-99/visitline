# Visitline — proposed scope

A small event host turns disconnected access observations into an understandable route card for a visitor's stated requirements.

## The Unique Kernel
An end-to-end visit depends on every recorded segment. A staircase can make a route incompatible; an unmeasured doorway makes it unconfirmed. Recording or changing one observation updates the whole route and explains the cause.

## Who It's For
Hosts of small workshops, talks and community events who currently publish a venue name and a short access statement. Visitors need the relevant details before deciding whether to attend. Actual interviews with these groups have not been performed.

## The Core Loop
Open an event → inspect its connected routes using stated visitor checks → locate the first incompatible or missing observation → update the host's record → review the visitor view → export a self-contained card and editable source record.

## Inspiration & Identity
The product should feel like a clear event information sheet with a route diagram. Calm, readable, precise. The diagram must explain a decision, not act as decoration. This is an agent-proposed design direction under the user's delegation.

## Why This Matters to the Learner
The user asked for data-driven concept selection, challenged weak differentiation and authorized a broader search. This concept follows that request. No personal disability, event-hosting experience or learning outcome is inferred.

## What "Working" Looks Like
A fictional event starts with one incompatible route and one unconfirmed route. A missing measurement is recorded; the visitor card updates. A stricter visitor requirement changes the result. The exported record reopens with the same inputs and results. The exported HTML is readable offline.

## The POC Boundary
One local event, up to four routes, a fixed set of visit stages, manually recorded widths/steps/open status and observation notes; visitor-selected checks; explicit unknowns; accessible printable HTML and editable JSON export/import. All demo data is fictional.

## Later
Evaluation with disabled attendees and event hosts; additional access needs; richer indoor maps; event publication and updates; photos with explicit consent.

## Explicitly Cut
Automatic dimension inference, legal compliance labels, claims of physical safety, universal accessibility scores, route navigation, live maps, account systems and runtime AI. None is needed to prove this mechanism, and several would require evidence unavailable here.

## Approval and evidence
This is a proposal made before code. The user delegated concept selection using research; they have not personally approved this document or tested the app. The prototype is authorized by the user's request to create and verify the best supported entry. Do not attribute agent choices or tests to the learner.
