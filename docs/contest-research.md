## Decision-relevant facts

This is Devpost's learning challenge at [learn-ai-basics.devpost.com](https://learn-ai-basics.devpost.com/). Its purpose is to practice planning with AI while making a small app that completes one useful function. The required AI use is the Devpost Learn Skill Pack during development; no specific cloud, model API or AI feature inside the app is specified. Treat that last statement as a reading of the published requirements, not a separate organizer guarantee.

The overview requires a fresh project begun in an empty folder, actual Skill Pack use, and the generated scope, PRD and spec in its public repository. It explicitly says reviewers will not clone or run code: the working demonstration must carry the evidence. [Official overview](https://learn-ai-basics.devpost.com/)

## Organizer learning and authorship constraints

The [official pack README](https://github.com/challengepost/learn-ai-basics) describes roughly 2–4 hours of active work and a proof-of-concept boundary. Its sequence is `1-start`, `2-scope`, `3-prd`, `4-spec`, `5-build`, `6-ship`. Planning docs record actual learner decisions; `status: approved` needs a clear approval, not silence or an agent's assumption. The build adds a checklist, review and learning wrap-up/app map. A personal learner profile stays out of public commits by default. Deployment and peer feedback are optional.

The shipping skill explicitly says: **“Submission copy and any optional peer feedback must be human-written, even on request.”** The entrant writes the name, short description, other submission answers and exit survey. The agent can interview, identify gaps and correct spelling/grammar; it may not draft, paraphrase, rewrite or turn a brain dump into public copy. It may perform authorized technical publishing/submission mechanics. This is an explicit curriculum constraint, distinguished here from the legal rules' eligibility language. [Official `6-ship` skill](https://github.com/challengepost/learn-ai-basics/blob/main/skills/6-ship/SKILL.md)

The onboarding skill checks for a dedicated fresh project, prevents inventing learner intentions, and keeps consequential decisions with the learner. Placeholder planning files or retroactively invented interviews would not demonstrate this learning process. [Official `1-start` skill](https://github.com/challengepost/learn-ai-basics/blob/main/skills/1-start/SKILL.md)

## What would convincingly exceed the minimum

The following are **researcher's inferences and acceptance proposals**, not hidden judge preferences or a predicted winning formula.

| Dimension | Convincing evidence beyond the minimum |
| --- | --- |
| Design | A focused, understandable core journey with readable states, sensible defaults, keyboard access and useful recovery when realistic input fails. Polish the one journey instead of adding disconnected features. |
| Potential Impact | Identify a concrete recurring task from the learner's experience. Demonstrate the original difficulty and show the app resolving it. Quantify benefits only if actually measured. |
| Innovation/Idea | Compare a few relevant current alternatives after concept selection. Name a specific workflow or mechanism difference and demonstrate it. Avoid unsupported first-ever claims. |
| Presentation | Let real interactions establish the result. Start with the audience/problem, show input-to-result, then connect the outcome to its usefulness and one authentic learning decision. Keep text/media claims consistent. |
| Learning intent | Show where scope, a requirement or an architectural decision changed implementation; preserve honest verification and revision evidence. The learner should be able to explain the resulting app. |

The explicit sponsor goal is a reusable planning habit and intentional collaboration with AI. It is reasonable to infer that authentic decisions and coherent execution support that story. Feature count, plugin count, production infrastructure and dramatic claims receive no stated scoring advantage. No separate Technical Implementation criterion is published in the current rules.

Devpost's general advice favors an immediately understandable narrated screencast and showing resolution to the original problem. This supports the presentation strategy; it is not extra contest policy. [Video best practices](https://help.devpost.com/article/84-video-making-best-practices), [Devpost CEO's demo guidance](https://info.devpost.com/blog/how-to-present-a-successful-hackathon-demo)
